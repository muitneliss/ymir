# Taskfile Guideline

Read this whenever the `taskfile` concern is in scope — during the interview (to
ask the `wraps` question and propose the task list) and during
`ymir apply taskfile` (to generate `Taskfile.yml`). It is the single source of
truth for what `concerns.taskfile.*` means and how it becomes a file.

The runner is [Task](https://taskfile.dev) (`go-task`) — **only** Task. Ymir does
not generate `Makefile`s or `justfile`s; a project that wants one skips this
concern.

## Why the harness has this concern

Every other concern produces a command someone has to remember: the linter's
invocation, the test runner's flags, the build. Without one entrypoint those
commands get copied into a README, a CI step, and a `CLAUDE.md` bullet, and then
drift apart. The Taskfile is the **one owner** of "how this repo is run": CI
calls `task lint`, the agent calls `task lint`, the human calls `task lint`, and
the command text lives in exactly one file.

That is also why it is worth skipping: a repo whose `package.json` scripts are
already that single owner gains a layer and loses nothing by saying no. Apply
YAGNI (`status: skipped` with a reason) rather than forcing it.

## `wraps` — who owns the command text

Required when the concern is captured. It decides what goes inside `cmds:`.

| `wraps` | Each task runs | Pick it when |
|---|---|---|
| `commands` (default recommendation) | the tool directly — `cmds: ["bunx biome ci --error-on-warnings ."]` | there are no existing scripts worth preserving, or they are thin aliases; the Taskfile becomes the single owner |
| `scripts` | the existing script — `cmds: ["bun run lint"]` | `package.json` scripts (or a `Makefile`) already exist and other tooling, docs, or humans depend on them; Task becomes a uniform front door without a second copy of the command |

Never generate both: with `wraps: commands`, do not also add a duplicate
`package.json` script for the same action, and with `wraps: scripts`, do not
inline the tool invocation into `cmds`. Two copies of a command is the exact
failure this concern exists to prevent.

## Task names

Prefer the names the project already uses; otherwise this is the expected set.
Only generate the ones in `concerns.taskfile.tasks[]` — an empty task is worse
than a missing one.

| Name | Does |
|---|---|
| `default` | `task --list` — always generate it (see below) |
| `lint` | the `lint` concern's command, as produced by that concern's playbook section |
| `lint:fix` | the fixer, where the tool has one |
| `test` | the test runner |
| `build` | the build |
| `dev` | the local dev loop (watch / server) |
| `ci` | everything CI runs, in order — `cmds: [{task: lint}, {task: test}]` |

Namespace with `:` (`db:migrate`, `docker:build`). A task that exists only as a
building block gets `internal: true`.

## File shape

`Taskfile.yml` at the project root (Task also accepts `Taskfile.yaml`; if one
already exists, keep its spelling rather than adding a second file).

```yaml
version: '3'

silent: true

tasks:
  default:
    desc: List available tasks
    cmds:
      - task --list

  lint:
    desc: Lint the repo (fails on warnings)
    cmds:
      - bunx biome ci --error-on-warnings .

  test:
    desc: Run the test suite
    cmds:
      - bun test

  ci:
    desc: Everything CI runs
    cmds:
      - task: lint
      - task: test
```

- `version: '3'` is required, and is the schema version, not the Task version.
- `silent: true` at the top level stops Task from echoing each command before it
  runs, so the output is the tool's own. Drop it if the user wants to see the
  exact command (useful when debugging CI).
- **Every task gets a `desc`.** `task --list` prints only tasks that have one —
  a task without `desc` is invisible to both the user and the agent.
- The `default` task makes the bare `task` command a menu. It is the discovery
  surface an agent lands on when it opens an unfamiliar repo.

## Verified semantics (Task 3.53.1)

These are the behaviours that bite when a Taskfile is generated by inference.
Each was checked against 3.53.1, not assumed.

- **Every `cmds` entry runs in its own shell.** `cd foo` in one entry does not
  carry into the next (`cd /usr && pwd` → `/usr`, then `pwd` → the project
  root). To run somewhere else, set `dir:` on the task, or chain with `&&`
  inside a single entry.
- **`deps` run in parallel, not in order.** `deps: [lint, test]` starts both at
  once — fine for independent work, wrong for a pipeline. For ordering, list
  task calls in `cmds`: `cmds: [{task: lint}, {task: test}]`.
- **`task --list` hides tasks without `desc`**; `--list-all` shows them;
  `internal: true` hides a task from both.
- **`sources` + `generates` fingerprint a task** — a second run with unchanged
  sources is skipped and still exits 0. Only put them on tasks that really do
  produce files (a build); a `lint` task with `sources` will silently stop
  linting after the first clean run.
- **`{{.CLI_ARGS}}` forwards everything after `--`**: `task test -- --watch foo`
  makes `{{.CLI_ARGS}}` `--watch foo`. Use it so the task never becomes a
  straitjacket around the underlying tool.
- **An unknown task name exits 200**, not 1 — do not use `task <name>` as an
  existence probe in a script without checking the code.

## Installing Task

Task is a single binary. Give the user the line for their platform; do not add a
dependency to the project for it.

| Where | Command |
|---|---|
| macOS / Linux (brew) | `brew install go-task/tap/go-task` |
| any (npm) | `npm install -g @go-task/cli` |
| Go projects | `go install github.com/go-task/task/v3/cmd/task@latest` |
| CI / scripted | `sh -c "$(curl --location https://taskfile.dev/install.sh)" -- -d` (installs into `./bin`; `-b <dir>` to change it, and a version argument to pin) |

## In CI

When the `ci` concern is also captured, CI installs Task and then calls the
tasks rather than repeating their commands. For GitHub Actions use the official
action:

```yaml
- uses: go-task/setup-task@v1
  with:
    version: 3.x
- run: task lint
```

(`arduino/setup-task@v3` is the upstream this was forked from and works too —
prefer `go-task/setup-task` for new workflows.) For providers without an action,
use the install script line above in a `before_script`/`setup` step.

## Verify

After generating, from the project root:

```bash
task --list
```

It must exit 0 and list every entry in `concerns.taskfile.tasks[]` with its
description. Then run the tasks that are safe to run (`task lint`) and confirm
they behave the same as the commands they replaced.
